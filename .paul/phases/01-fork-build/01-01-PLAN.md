<objective>

## Goal
Turn the empty project repository at /home/peter/Dokumente/corel into a fork of upstream Inkscape. The fork must keep full upstream history, be pinned to a recorded base commit, build from source on this Ubuntu machine, and launch from a local install prefix. Add rebrand groundwork (placeholders and an inventory, with no behavior change) and get a decision on the fork's product name.

## Purpose
Every later phase (CMYK, PDF/X, Corel-style UI, tools, .cdr) needs a reproducible build of a known upstream base first. Keeping upstream history and isolating fork-only files under `fork/` keeps future upstream rebases cheap and GPL provenance clear. The name decision blocks plan 01-02, which applies the actual rebrand.

## Output
- Project repo = Inkscape upstream history plus remote `upstream`, local tag `fork-base`, and branch `main`.
- `fork/UPSTREAM_BASE` records the pinned commit SHA, the ref it came from, and the GTK major version.
- `fork/scripts/install-build-deps-ubuntu.sh`, `fork/scripts/build-local.sh` and `fork/scripts/run-local.sh` give a reproducible dependency install, build and run.
- A working binary at `install/bin/inkscape`, built from the unmodified base.
- `fork/cmake/ForkBranding.cmake` holds placeholder variables. It is included from the top-level `CMakeLists.txt` but nothing uses the variables yet.
- `.paul/phases/01-fork-build/branding-inventory.md` lists every rebrand touchpoint, as input for 01-02.
- The product-name decision is recorded at the checkpoint.

</objective>

<name>Task 1: Fetch upstream into project repo, pin base, record GTK major</name>
<files>fork/UPSTREAM_BASE, fork/README.md, .git/info/exclude (local, untracked)</files>
<action>
1. `cd /home/peter/Dokumente/corel`. The repo is NOT initialized yet: if `.git` is missing, run `git init -b main`. Then `git status --porcelain`; expect only `?? .paul/`. Stop and report if anything else is there.
2. Run `git remote add upstream https://gitlab.com/inkscape/inkscape.git`, then `git fetch --filter=blob:none --tags upstream master`.
3. Choose the base ref with this deterministic rule:
   a. Run `git grep -nE "gtkmm-(3|4)\.0" upstream/master -- CMakeLists.txt CMakeScripts/` to find the GTK major on master.
   b. Find the newest stable release tag: `git tag -l 'INKSCAPE_1_*' | grep -vE 'ALPHA|BETA|RC|pre' | sort -V | tail -1`. Run the same gtkmm grep on that tag.
   c. If the newest stable tag already uses gtkmm-4.0, use that tag.
   d. Otherwise, if master uses gtkmm-4.0, use the current `upstream/master` commit. This matches the PROJECT.md GTK4 decision and avoids porting all Phase 4 UI work from GTK3 to GTK4 later.
   e. Only if neither uses gtkmm-4.0, use the newest stable tag and add a note in fork/README.md flagging the PROJECT.md GTK4 constraint.
4. Run `git switch -C main <chosen SHA>`; `.paul/` stays untracked and does not conflict. Then `git tag fork-base <chosen SHA>`.
5. Run `git submodule update --init --recursive`.
6. Write `fork/UPSTREAM_BASE` with key=value lines: `sha=`, `ref=` (tag name or `master@<date>`), `gtk_major=`, `fetched=2026-10-20`.
7. Write `fork/README.md`. It must say: this is a GPL-2.0-or-later fork of Inkscape; credit upstream and link it; explain the `fork/` directory convention (all fork-only files live here, upstream files are touched minimally); give the rebase procedure (`git fetch upstream && git rebase --onto <new-base> fork-base main`); and note that the product name is TBD (see the checkpoint). Put the GPL SPDX line in an HTML comment at the top.
8. Append `build/`, `install/` and `.profile/` to `.git/info/exclude`. Do not edit the upstream `.gitignore`; that would add upstream-diff noise.

Avoid:
- Cloning into a subdirectory. A nested repo inside the project repo breaks PAUL tracking and the rebase flow.
- Squashing or shallow-cloning history (`--depth`). Rebases onto upstream and GPL provenance need ancestry. `--filter=blob:none` is fine: full commits, lazy blobs.
- Pushing to any remote. Publishing is outward-facing and out of scope.
- Committing `.paul/` in this task. Leave it to the PAUL unify step.
</action>

<name>Task 2: Install build deps, build unmodified base, smoke-run</name>
<files>fork/scripts/install-build-deps-ubuntu.sh, fork/scripts/build-local.sh, fork/scripts/run-local.sh</files>
<action>
1. Derive the package list from upstream's own source of truth, not from memory. Inspect `.gitlab-ci.yml`, `INSTALL.md`, and any install script referenced in `buildtools/` or by the CI docker image (`inkscape-ci-docker`, `install_dependencies.sh`). Write `fork/scripts/install-build-deps-ubuntu.sh` (bash, `set -euo pipefail`, GPL SPDX header) running `sudo apt-get install -y --no-install-recommends ...` with that list. At minimum it should cover:
   - toolchain: build-essential, cmake, ninja-build, ccache, pkg-config, gettext, git
   - GTK-major packages matching `gtk_major` from `fork/UPSTREAM_BASE`: for 4, libgtkmm-4.0-dev and companions (libglibmm-2.68-dev, libcairomm-1.16-dev, libpangomm-2.48-dev, libsigc++-3.0-dev); for 3, libgtkmm-3.0-dev and libgspell-1-dev
   - libraries: libboost-dev, libboost-filesystem-dev, libboost-stacktrace-dev, libdouble-conversion-dev, libgsl-dev, liblcms2-dev, libcdr-dev, libvisio-dev, libwpg-dev, librevenge-dev, libpoppler-glib-dev, libpoppler-private-dev, libpotrace-dev, libxml2-dev, libxslt1-dev, libharfbuzz-dev, libpango1.0-dev, libcairo2-dev, libfontconfig-dev, libepoxy-dev, libjpeg-dev, libpng-dev, libreadline-dev, libgtest-dev
   - Python extension runtime: python3-lxml, python3-numpy, python3-tinycss2
   - apt-file, for the step-3 loop
   The script must be idempotent. It must not enable deb-src or run `apt build-dep inkscape`: Ubuntu's packaged Inkscape may use a different GTK major and pull the wrong dependency set.
2. Write `fork/scripts/build-local.sh` (SPDX header, `set -euo pipefail`). It should run:
   - `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_INSTALL_PREFIX="$PWD/install" -DCMAKE_C_COMPILER_LAUNCHER=ccache -DCMAKE_CXX_COMPILER_LAUNCHER=ccache`
   - `ninja -C build -j"${JOBS:-$(nproc)}"`
   - `ninja -C build install`
3. Run the deps script; the human approves sudo. Then run the build script. If configure fails on a missing package, run `apt-file search <module>.pc` (or `<header>.h`), add the package to the deps script and re-run. Keep looping until configure succeeds; every added package stays in the script so the script remains the reproducible source of truth. If linking gets OOM-killed, re-run with `JOBS=4`.
4. Write `fork/scripts/run-local.sh`. It should `export INKSCAPE_PROFILE_DIR="$PWD/.profile"` and then `exec "$PWD/install/bin/inkscape" "$@"`. This isolates prefs so the dev build never reads or migrates the user's real `~/.config/inkscape`.
5. Smoke test: create a minimal SVG at `/tmp/fork-smoke/in.svg` (a 100x100 red rect), export it headless to PNG, then launch the GUI under `timeout 20`.

Avoid:
- `sudo ninja install`, or installing into /usr or /usr/local. That would collide with any system Inkscape, and AC-2 requires a local prefix.
- Changing any upstream source or CMake option to make the build pass. If the base truly fails to build, stop and report the decisive error line; do not patch. An unmodified base is the AC.
- Disabling optional features (`-DWITH_*=OFF`) unless a dependency is genuinely unavailable on this Ubuntu release. If you do, record each one with its reason in fork/README.md.
</action>

<name>Checkpoint: Decide fork product name</name>
<context>
The fork must not be named Inkscape (Inkscape's trademark policy) or use anything CorelDRAW-like ("Corel", "Draw"-suffixed names that echo CorelDRAW, Corel balloon motifs). 01-02 will apply the name to the binary, app-id, desktop file, config dir, gettext domain and about/splash screen. All candidates below are UNVERIFIED. Before you confirm, search EUIPO/USPTO trademarks, Flathub, GitHub, Debian/Ubuntu package names and the domain.
</context>
<options>
Option A: "Pressmark"
  Pros: signals print/prepress focus (CMYK, PDF/X), which is the differentiator. Two syllables, distinct in software.
  Cons: sounds less like a general illustration tool; possible existing print-industry trademarks.

Option B: "Kontur"
  Pros: short, means "contour/outline" in German and other languages, fits vector drawing, easy binary name `kontur`.
  Cons: generic word, so weak trademark and search visibility; existing companies/products share the name, so collision risk is high.

Option C: "Linea"
  Pros: "line" in Latin/Italian, elegant, neutral, works internationally.
  Cons: widely used brand word (apps, fonts, companies), so search visibility is low and the app-id/domain may be taken.

Option D: User-supplied name
  Pros: full ownership; can be checked against trademarks before choosing.
  Cons: needs the same checks; delays 01-02 until done.

Recommendation: shortlist A or D. Print focus is the core value, and a coined or compound word is easier to search and defend than a generic dictionary word.
</options>
